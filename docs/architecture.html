4 · ScreenWarden core

Two checkpoints, one policy

Clean the screen

sanitize_screen: removes hidden and instruction-like text; flags spoofed login, payment and overlay screens; records OTPs

→

Agent's model decides

Sees only the cleaned screen, with outside text marked as data

→

Check the action

check_action: ALLOW / BLOCK / ASK_HUMAN, with a data-flow check against the goal and an OWASP tag (ASI01, ASI02)

Taint memory

Guard remembers outside text, instructions and codes across screens and agents

policy.yaml

One generic policy for every app, with no per-app rules to maintain

Screen learning

ProfileGuard: labels the buttons of apps the policy does not know. Can only make decisions stricter

Profile cache

ProfileStore: one label set per screen layout, so Claude is asked once per layout

Decision log

JSON lines: rule, OWASP tag, exact model ID; digits masked

optional, with --learn: structure only, never screen text →

What we wrote

Four entry points, the core (cleaning, checking, taint, policy, screen learning, log), the test agent, the attack lab and the tests. Python 3.11, with PyYAML as the only required dependency.

What the customer brings

The agent and its model. ScreenWarden does not depend on the model; the same guard stopped scripted attacks and ran under Claude and four local models.

What stays outside

The phone, the apps, adb, and the Anthropic API. The API is used only with --learn, and only the screen's structure is sent.
